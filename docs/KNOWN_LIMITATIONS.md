# 已知限制

发布说明只讲这一版改了什么。「这一版仍然做不到什么」记在这里，按主题归类，跨版本累积。

新增一条时写清楚**现象**和**为什么**，读者才能判断它会不会影响自己。某条不再成立时直接删掉，不要留「已修复」的注脚——历史在 git 里。

## 通知

- **heads-up 弹窗宽度由系统决定**。任意长的问题无法在弹窗里完整显示，展开通知或点进会话才能看全文。
- **「会话完成」通知不强制横幅**。它进入通知栏；是否弹横幅由系统通知频道决定，不像 ask 那样强制 heads-up。
- **后台 watcher 需要 App 先知道这个回合**。局域网后台提醒要求 App 在退到后台前已经看到运行中/待处理回合。在电脑上新开始、手机完全不知情的回合，Android 12+ 不允许后台临时启动前台服务去补抓。

## 震动

- **打开「回答开始与结束」后，切换会话可能多震一次**。该开关默认关闭。打开后，若会话从缓存水合或历史合并中重建了行，新的行 id 会被当成「新回答开始」而震一下——用户并没有发出新问题。根因是 `useStreamHaptics` 只拿到行数组，缺少「这是真实流式开始」的信号；干净的解需要把水合/历史状态传进去，属于更大的重构。默认关闭把影响面压到主动开启的用户。

## 连接

- **回前台会重建一次事件流**，即使流是健康的。这是修复「后台断连后对话不再更新」的代价：僵尸连接的 `readyState` 仍是 `OPEN`，没有更低成本的判定手段。重建带 cursor，不丢不重（见 #95）。
- **`phase !== "connected"` 时回前台不自愈**。`reassess` 在链路状态不是 connected 时直接返回，属于既有行为，未纳入本次范围。
- **应用内「完整界面」不会把内核新下发的 cookie 写回 WebView**。局域网的完整界面走 loopback 代理（否则 VPN 会把私有地址吞掉），代理转发时会补上配对时保存的 device cookie，所以页面能正常打开；但响应里的**所有** `Set-Cookie` 都只进代理自己的内存 jar，`writeResponse` 不把它们回写给页面——页面本身从来没收到过 cookie。首次访问不受影响，只要内核的会话 cookie 发生轮换（或任何依赖页面侧 cookie 的逻辑），就可能失效。彻底修需要让 `writeResponse` 支持多个 `Set-Cookie` 头，那条路径被所有响应共用，改动更大。

## 内容渲染

- **超宽表格的固定列在窄屏下会被挤压**。长内容列没有换行上限时会把短列挤到只剩一个字宽；`table-wrap` 已支持横向滚动，但列宽分配仍由浏览器决定。
